think + function

Call an LLM like a typed Python function.

Write a signature and a docstring. thunc sends them to a model, parses the answer into your return type, and asks again when it doesn't fit. Standard library only.

The aim

Most LLM calls in real code are small. They should look small.

Classify this ticket. Score that answer. Pull these fields out of an email. Each one needs the same plumbing: build a prompt string, send it, parse the reply, handle the reply that isn't valid JSON, try again. thunc's aim is to make that call look like any other function in your program: typed, readable, and loud when it fails.

-> int

The signature is the contract

The docstring is the prompt, the parameters are the inputs, and the return annotation is the type you get back.

ThuncError

Fails loudly

A wrong-shaped answer is sent back to the model to fix. If it still doesn't fit, you get an exception, never a silent default.

stdlib

Nothing extra to install

The core uses the standard library only. Provider SDKs are optional extras you add when you need them.

<inputs>

User data stays data

Arguments are sent separately from the instructions, so text from users can't quietly rewrite your prompt.

How it works

One decorator, four steps.

  1. Docstring → instructions

    The docstring (or an instructions= string built in code) tells the model what to do.

  2. Arguments → inputs

    Each argument is sent in its own block, marked as data, never pasted into the instructions.

  3. Return type → reply format

    The annotation tells the model the exact shape to answer in, such as an integer, one of these labels, or an object with these fields.

  4. Parse, check, retry

    The reply is parsed and checked, including your own ensure= rule. Problems go back to the model; after the retries, ThuncError.

Typed results

str, bool, int, float, Literal[...], list[T], dict[str, T], T | None and dataclasses, built into real instances.

ensure=

Add your own rule, like ensure=lambda n: 1 <= n <= 5. A failed check is sent back and retried.

thunc.map

Run calls in parallel and keep the input order. Each call takes seconds, so this is the main speed lever.

async def

Declare the function async and you get an awaitable.

trace=

configure(trace="calls.jsonl") logs every prompt, answer, retry and timing.

mypy · Pyright

Signatures and return types are real Python, so your type checker sees them.

Two ways to write a prompt

Fixed prompts read like code. Built prompts stay in code.

@thunc.function

When the prompt is fixed. Reusable and fully typed.

@dataclass
class Order:
    order_id: str
    amount_eur: float | None = None

@thunc.function
def category(ticket: str) -> Literal[
    "bug", "billing", "other"]:
    """Classify this support ticket."""
    ...

@thunc.function
def find_order(ticket: str) -> Order | None:
    """Extract the order, or null if none."""
    ...

labels = thunc.map(category, tickets)

thunc.call(...)

When the prompt is built in code: from config, in a loop, from a file.

for lang, rules in STYLE_GUIDES.items():
    text = thunc.call(
        f"Translate into {lang}. Style: {rules}",
        {"release_note": note},  # data
    )

score = thunc.call(
    "Score this answer from 0 to 3.",
    {"answer": answer},
    returns=int,
    ensure=lambda n: 0 <= n <= 3,
)
Prompt injection

Where user text goes matters.

In a live test, the same hostile email was sent to the model two ways. The only difference was where the email went.

3/3times the email took over the model
thunc.call(f"Summarise this email: {email}")
0/3times, with the email passed as an input
thunc.call("Summarise this email.", {"email": email})

A small live test, not a guarantee. @thunc.function always sends arguments as inputs; with thunc.call, keep your own text in the instructions and everything from users, files or the web in the inputs.

Backends

Your model, your choice.

Pick one with thunc.configure(backend=...) or THUNC_BACKEND. With nothing set, an ANTHROPIC_API_KEY or OPENAI_API_KEY in the environment picks one for you.

Claude API

Anthropic's API, with your key.

thunc[anthropic]

OpenAI API

The Responses API, with your key.

thunc[openai]

Local models

Any server that speaks the OpenAI API, via OPENAI_BASE_URL. Tested with LM Studio and gpt-oss-20b.

thunc[openai]

Claude Code · Codex

Your local CLI login. No API key needed, which makes it handy for trying thunc out.

Status

Beta, and built in the open.

thunc is at v0.1. It works, it's tested, and the API may still change. Here's where things stand.

Works today

  • Typed results, retries and ensure=
  • Claude, OpenAI, local and CLI backends
  • Parallel calls, async and tracing

Up next

  • Enum return types
  • Pydantic models as return types
  • Caching and record/replay
  • Planned for 0.2: agents

Known limits

  • No caching yet, so repeated calls cost again
  • Literal results from thunc.call are typed as Any
  • Docstrings vanish under python -OO; use instructions=
